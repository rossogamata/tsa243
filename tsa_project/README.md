## Концепція

Замість ізольованих лабораторних робіт — курсанти будують **реальну production-подібну інфраструктуру** протягом усього курсу. Кожне заняття додає новий шар поверх попереднього. Результат — повноцінне робоче середовище, розгорнуте власноруч від чистого Ubuntu-шаблону до мережі зі спільними сервісами, VPN і моніторингом.

Помилки мають реальні наслідки: зламаний DNS — проблема для всіх. Це природній стимул бути уважним і розуміти що робиш.

## Git Workflow

### Структура гілок

```
main  ← викладач: еталонні конфіги, матеріали занять
├── petrenko
├── shevchenko
├── kovalenko
└── ...  (29 гілок, одна на курсанта)
```

Гілка курсанта — це його **особисте портфоліо** за весь курс. Тут накопичуються звіти по кожній практичній роботі, конфіги, скрипти.

### Захист практичних робіт через Pull Request

Кожна практична або групова робота захищається одним PR:

```
1. Курсант виконує роботу на VM
2. Документує в reports/lessonX_Y.md  (що зробив, команди, скріншоти, висновки)
3. Комітить у свій branch:
       git add reports/lesson5_6.md
       git commit -m "lesson5_6: мережева конфігурація"
       git push origin petrenko
4. Відкриває Pull Request: petrenko → main
5. Викладач перевіряє, залишає коментарі
6. Approve = залік по роботі
```

PR не обов'язково мерджиться — він використовується як **інструмент перевірки і фідбеку**.

## Спільні сервіси — колективна відповідальність

Спільні VM (`ns1`, `mail`, `proxy`, `mon`) налаштовує викладач як базову інфраструктуру. Курсанти **розширюють** її:

- `ns1` — кожен додає свій A-запис у зону `tsa243.lab`
- `mail` — кожен створює власну поштову скриньку
- `proxy` — кожен додає свій Nginx virtual host
- `mon` — кожен запускає node_exporter на своїй VM

Конфліктні ситуації (два курсанти одночасно редагують `named.conf`) є **навчальним матеріалом** — природнє пояснення навіщо потрібен IaC і версіонування конфігів.

## Міст до наступного курсу

**Поточний курс (Варіант A — "Repo як щоденник"):**
Курсанти роблять зміни вручну на VM, документують у PR.

**Наступний курс: Docker / Ansible / Terraform / CI-CD (Варіант B — "Repo як джерело правди"):**
- Конфіги спільних VM переїздять у репозиторій
- PR = зміна інфраструктури як коду
- CI/CD pipeline застосовує зміни автоматично
- Ту саму мережу `tsa243.lab` вони будуть керувати Ansible playbooks і Terraform

Курсанти не вивчають абстрактний Ansible — вони **автоматизують інфраструктуру яку самі побудували руками**.
